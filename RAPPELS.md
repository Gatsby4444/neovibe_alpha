| 11 | **HÉBERGEMENT — quand et comment quitter (ou garder) Supabase** | Question posée par Jay le 2026-07-26. **Ce qu'on a déjà** : Supabase n'est PAS qu'une base — c'est Postgres + API REST générée + auth + stockage + temps réel + cron + Edge Functions. Le code serveur EXISTE et vit dans `supabase/migrations/` : **71 politiques RLS** (toute la sécurité du graphe social), **47 fonctions SQL**, **6 triggers**, **3 tâches cron** (dont le TTL 24 h). **Le vrai axe n'est pas « VPS ou Supabase » mais « managé ou auto-hébergé »** : un VPS ne donne pas plus de puissance, il transfère l'exploitation (Postgres, sauvegardes ET tests de restauration, TLS, auth maison = risque de fuite, supervision, correctifs). **Ce qui limitera vraiment** : le stockage et la bande passante SORTANTE, pas le SQL. La limite de 50 Mo/fichier est une limite de PLAN, pas d'architecture. Le TTL 24 h borne naturellement le stockage — **le feed local (chantier #10) fera sauter cette borne** : c'est là qu'est la bascule économique. **Ordre de migration, par morceaux et jamais d'un bloc** : (1) les médias vers un stockage objet à egress bon marché (Cloudflare R2, Backblaze B2) ; (2) les traitements lourds (transcodage, fan-out de notifications) vers un service de conteneurs (Fly.io, Railway, Render) plutôt qu'un VPS nu ; (3) Postgres en dernier — Supabase étant du Postgres standard, les migrations se rejouent ailleurs, il n'y a pas d'enfermement au niveau de la base. **Trois déclencheurs à surveiller** : la facture stockage/bande passante devient le premier poste ; le feed local arrive avec du contenu durable ; un besoin que Postgres + Edge Functions ne couvrent pas. | 2026-07-26 |
