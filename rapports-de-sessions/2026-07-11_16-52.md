### Choix d'implémentation signalés (ambiguïtés de spec tranchées, cf. section 8 de la spec)

- **Recommandation A→B→C — désignation de C** : la spec ne dit pas comment B désigne C
  sans annuaire ni accès à la liste des connexions de A. Choix : B décrit C en texte libre
  (`target_hint`) dans sa demande à A ; A choisit le vrai C parmi SES connexions au moment
  de transmettre. Le plus conforme au principe "pas de découverte par annuaire".
- **Refus de recommandation** : enregistré `declined` en base, mais jamais affiché à B
  (le client de B traite tout ce qui n'est pas accepté comme une expiration silencieuse).
- **Réinitialisation des 3 messages de proximité** : les messages expirant à 24h, le
  compteur repose sur les messages non expirés → réinitialisation naturelle, cohérente
  avec "nouvelle rencontre BLE réinitialise".
- **Expiration des demandes BLE** : `expires_at` à 90 s rafraîchi par le client émetteur
  tant que le pair est détecté ; sortie de portée → plus de refresh → expiration.
- **Oneshot / One of One en bibliothèque** : interdits (contradiction avec vue unique /
  exclusivité). Standard/Hot/BeReal publiables.
- **Hot — mise en avant** : implémenté comme `hot_boosted` privé chez le destinataire si
  la Card est ouverte < 2 min après réception (badge/tri dans SON interface, rien de
  public). **À valider par Jay** (la spec demandait validation si comportement flou).
- **Purge Storage** : la purge cron supprime les lignes DB ; les fichiers média orphelins
  deviennent inaccessibles (policies liées aux lignes) mais ne sont pas encore effacés du
  bucket — nettoyage physique à ajouter plus tard (edge function).

## Difficultés rencontrées / erreurs

- Machine de dev sans toolchain mobile : Flutter, JDK et Android SDK absents.
  Solution : installation locale scriptée dans `C:\Charles\dev\` (pas de droits admin requis).
- `sdkmanager --licenses` ignore le pipe PowerShell (`"y" | cmd`) : utiliser une
  redirection cmd (`cmd /c "sdkmanager.bat --licenses < yes.txt"`).
- Flutter 3.44 exige Android SDK **36** (le doctor le dit après coup) : installer
  `platforms;android-36` + `build-tools;36.0.0` d'emblée.
- **Riverpod 3** : `AsyncValue.valueOrNull` n'existe plus → `.value` (qui ne throw plus).
- **flutter_blue_plus** : `advertisementData.msd` est une liste ; la map fabricant
  s'appelle `manufacturerData`.
- Flutter 3.44 déprécie `RadioListTile.groupValue/onChanged` → wrapper `RadioGroup`.
- Le RPC `resolve_ble_tokens` ne renvoyait pas le token scanné → impossible d'associer
  profil ↔ trame BLE côté client. Corrigé par migration (le token est renvoyé : pas de
  fuite, l'appelant le possède déjà).

## Correctif post-test (retour de Jay)

- **Symptôme** : impossible d'ajouter du contenu non textuel (avatar, Card, photo) —
  erreurs Postgres. Le texte fonctionnait.
- **Cause** (logs Postgres) : `infinite recursion detected in policy for relation
  "cards"/"card_deliveries"`. Les policies des deux tables se référençaient
  mutuellement. Effet aggravant : la policy SELECT du bucket Storage `cards` joignait
  ces tables → l'INSERT Storage (qui évalue les policies SELECT au RETURNING) échouait
  pour TOUS les buckets, d'où l'échec de tout upload.
- **Fix** : migration `fix_cards_policy_recursion` — helpers `security definer`
  (`private.owns_card`, `private.has_card_delivery`, `private.can_view_card_file`)
  à la place des sous-requêtes croisées. Vérifié en SQL avec le rôle `authenticated` :
  insert+returning, selects et storage OK.
- **Leçon** : quand deux tables se référencent dans leurs policies RLS, toujours passer
  par une fonction security definer d'un côté. Et tester les INSERT `.select()` (RETURNING)
  qui évaluent les policies SELECT.
- Correctif 100 % côté serveur : **l'APK v0.1.0 existant reste valable**.
- Reste à tester par Jay (2 appareils requis) : Ping BLE, messagerie proximité,
  recommandations, groupes, Waves.
