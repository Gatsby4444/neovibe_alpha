## Modifications apportées

### Étape 4 — vidéo double GPU (v0.9.12)

**`Camera2Gl.kt`** (moteur GPU, par caméra) :
- Nouvel encodeur vidéo : `startRecording()` / `stopRecording()`.
  `setupEncoder()` crée un `MediaCodec` H264 (surface d'entrée), une **surface
  EGL adossée à cette entrée** (même `eglContext` + `eglConfig` mémorisé → la
  texture OES et le shader sont partagés, aucun flux caméra supplémentaire), et
  un `MediaMuxer` → un `.mp4` par caméra.
- Refactor : le corps de dessin commun est extrait dans `drawCurrentFrame()`
  (viewport + clear + programme + uniformes + draw), appelé pour l'aperçu ET
  pour l'encodeur. `onFrame()` dessine désormais dans DEUX surfaces : l'aperçu
  (swap), puis — si `recording` — la surface d'entrée du codec (`encodeCurrentFrame`),
  avec le **timestamp du capteur** (`SurfaceTexture.timestamp`) via
  `EGLExt.eglPresentationTimeANDROID`.
- `drainEncoder()` : sort les paquets vers le muxer (gère `INFO_OUTPUT_FORMAT_CHANGED`
  → `addTrack`+`start`, ignore le paquet `CODEC_CONFIG`, `BUFFER_FLAG_END_OF_STREAM`).
  Drain non bloquant par image ; drain bloquant à l'arrêt (EOS).
- `releaseEncoder()` : stoppe/libère codec + muxer + surface EGL de l'encodeur et
  **remet l'aperçu courant** (le rendu continue). Appelé aussi dans `close()` si
  un enregistrement traînait.
- Débit : `VIDEO_BITRATE = 6 Mb/s` (test local, pas d'upload). NOTE laissée dans
  le code : réconcilier avec le plafond Supabase (RAPPELS #7) à l'étape 5.

**`NativeCamera.kt`** : cas de canal `startGlDualVideo` / `stopGlDualVideo`
(sur `ioExecutor`, hors thread principal) : démarrent/arrêtent les deux encodeurs
(`glBack` + `glFront`) ; repli propre si un des deux refuse (`GL_VIDEO_FAILED`).

**`native_camera.dart`** : `startGlDualVideo()` / `stopGlDualVideo()`
(→ `({back, front})`).

**`gl_preview_test_screen.dart`** : en mode Double, bouton « Vidéo (2 faces) »

## Retour de test Jay (v0.9.12) + correctif lecture (v0.9.13)

**Retour** : le double flux live marche ; mais en lecture, la vidéo **arrière
paraît figée** (avant animée) et **les deux sont écrasées en largeur**.

**Diagnostic (logs à l'appui) — la CAPTURE est bonne, le défaut est en LECTURE :**
- Les deux encodeurs démarrent (« encodeur vidéo démarré 720×1280 @30 » ×2) et
  écrivent **~37 Mo chacun** (arrière 36941 Ko, avant 37057 Ko) pour ~51 s à
  6 Mb/s. Une vidéo figée pèserait quasi rien (H264 compresse une image fixe à
  ~zéro) → **les deux fichiers contiennent de la vraie vidéo animée.**
- Les deux threads `nv-gl` rendent en continu tout du long (120→1800 images,
  deux paliers à chaque étape) → aucune caméra affamée.
- Donc : (1) « arrière figée » = **deux `VideoPlayer`/ExoPlayer simultanés**, un
  travers connu de Flutter où l'un reste bloqué sur sa 1re image ; (2) « écrasé
  en largeur » = ma lecture mettait **deux portraits 9:16 côte à côte** sur un
  écran portrait.

**Correctif (v0.9.13) — `_DualVideoPlayback` réécrit** : un **seul lecteur à la
fois**, plein écran, ratio respecté (`AspectRatio`), bascule Arrière/Avant
(`SegmentedButton`). Le fichier caché est libéré → jamais deux lecteurs
simultanés. **L'encodeur natif n'est PAS touché** (un seul changement à la fois
— leçon des « 3 releases perdues à deviner »). Si l'arrière est encore figée
après ça, ce sera l'encodeur ; mais les 37 Mo indiquent que non.

`flutter analyze` 0 issue, APK **59,0 Mo**, version **0.9.13+103**.
